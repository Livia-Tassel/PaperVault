# 项目定位：面向科研人员的智能论文解析、图表提取与知识资产管理系统
# 首发平台：Windows 11 x64
# 后续平台：macOS、Linux
# 项目类型：完整桌面应用
# 开发目标：可长期使用、可安装、可维护、可扩展的专业软件

============================================================
一、你的角色与总体任务
============================================================

你是一名具有丰富经验的全栈工程师、桌面应用开发工程师、
文档智能处理工程师和软件架构师。

现在请你独立设计并开发一款名为 PaperVault 的专业桌面软件。

PaperVault 面向科研人员，核心目标是：

将传统 PDF 论文转化为可以长期管理、检索、预览、
编辑和复用的结构化知识资产。

用户只需要上传论文 PDF，软件就应当尽可能自动完成：

1. 解析论文基本信息。
2. 提取论文正文及章节结构。
3. 识别并导出论文中的 Figure。
4. 识别并导出论文中的 Table。
5. 提取 Figure 和 Table 对应的 Caption。
6. 保存图表在原始 PDF 中的位置。
7. 将解析结果组织成结构化论文库。
8. 支持跨论文全文搜索、图片搜索和表格搜索。
9. 支持图片、表格、正文等资源的独立导出。
10. 支持从搜索结果直接跳转到原始 PDF 对应位置。

该软件必须真正具备上述能力，而不是通过静态数据、
模拟 API 或占位界面展示预期效果。

请充分利用现有成熟开源项目，避免重复造轮子。

开发时优先保证：

正确性 > 数据安全 > 核心功能完整性 > 易用性 >
可维护性 > 性能 > 视觉效果 > 高级功能。

最终必须交付一个真实可运行的软件项目。


============================================================
二、产品设计理念
============================================================

PaperVault 不是传统 PDF 阅读器，也不是普通文献管理软件。

它的核心价值在于：

让论文中的 Figure、Table、正文和其他内容成为
可以独立管理、检索和复用的知识资产。

请始终遵循以下原则。

【1】Local First

默认所有论文和解析结果保存在用户本地。

核心功能不依赖云端服务，也不强制要求 API Key。

未经用户明确同意，不得将论文内容上传至第三方服务。

【2】Paper-Centric + Asset-Centric

软件同时具有两种视角：

论文视角：
用户按照论文管理和浏览自己的资料。

资源视角：
用户可以直接浏览全部论文中的 Figure 和 Table，
不需要先找到对应论文。

这两种视角必须相互关联。

【3】Traceability

每一项提取出来的资源必须能够追溯到原始论文。

尽可能保存：

- Paper ID
- Resource ID
- 原始文件
- PDF 页码
- Bounding Box
- 所属章节
- Caption
- 提取时间
- 使用的解析引擎与版本

用户点击任何图片或表格时，都应该能够打开原始 PDF，
并定位到对应内容。

【4】Non-Destructive

不得修改用户导入的原始 PDF。

所有解析结果、人工修正和导出操作必须独立保存。

重新解析论文时，也不能直接覆盖用户的人工修改。

【5】Graceful Degradation

PDF 解析并不总能成功。

如果部分图片或表格无法正确识别，
软件必须明确标注解析失败或需要人工校对。

不要编造不存在的图片、表格、作者、年份或其他元数据。

【6】长期可维护

这是一个准备长期使用的软件，不是一次性 Demo。

优先选择稳定、成熟、文档完善的技术方案。

避免不必要的微服务、分布式系统和复杂部署依赖。

PDF 解析引擎、数据库、前端界面和桌面运行时

============================================================
六、核心功能三：Figure 自动提取
============================================================

这是 PaperVault 的核心卖点之一。

用户上传论文后，
软件应当自动寻找论文中的 Figure。

对于每个 Figure，尽可能提取：

- Figure 编号
- 图片内容
- Caption
- 所在页码
- Bounding Box
- 所属论文
- 所属章节
- 原始 PDF 位置

例如：

Figure 3: Overall architecture of the proposed system.

应保存成独立资源：

figure_3.png

同时建立元数据记录。

【图片提取方式】

必须区分两种情况。

情况一：

Figure 是 PDF 中的嵌入式图片。

可以直接提取对应的图片对象，
同时保留其格式信息。

情况二：

Figure 由矢量图、文字、线条等元素组成。

此时不能仅依赖 PDF get_images()。

必须通过版面识别确定 Figure 区域，
然后将对应区域渲染为 PNG。

优先使用 Docling 的图片区域识别能力，
必要时结合 PDF 渲染工具完成裁剪。

支持导出分辨率设置，例如：

- 150 DPI
- 300 DPI
- 600 DPI

对于无法正确识别的 Figure，
允许用户手动在 PDF 上框选区域。

必须实现基本的人工裁剪修正功能。

用户应当能够：

1. 查看提取的 PNG。
2. 查看原始 Caption。
3. 查看原始 PDF 位置。
4. 重新调整裁剪框。
5. 重新生成 PNG。
6. 重命名资源。
7. 下载或复制图片。
8. 批量导出多个 Figure。

Figure 编号、Caption 和图片的匹配
不能只依赖简单的字符串猜测。

如果无法确定对应关系，
应当标记待校对。

对于 Figure 1(a)、Figure 1(b) 等多子图，
第一版优先正确提取完整 Figure，
后续再考虑自动拆分子图。


============================================================
七、核心功能四：Table 自动提取
============================================================

这是另一个核心卖点。

对于每个 Table，尽可能提取：

- Table 编号
- Caption
- 所在页码
- Bounding Box
- 表格内容
- 行列结构
- 所属论文
- 所属章节

每个 Table 至少支持三种导出形式：

1. CSV
2. HTML
3. PNG

CSV：

用于数据分析和 Excel。

HTML：

用于保留较复杂的表格结构。

PNG：

用于保留原始 PDF 中的视觉布局。

支持直接在软件内预览表格。

需要重点处理：

- 多级表头
- 合并单元格
- 空单元格
- 数值和文本混合
- 科学计数法
- 特殊数学符号
- 表格脚注
- 表格跨栏

注意：

CSV 本身无法完整表达合并单元格、
多级表头和表格脚注等复杂信息。

因此必须同时保留原始视觉截图和结构化信息。

如果解析结果可能丢失结构，
应提示用户检查。

【人工修正】

实现基本的表格编辑界面。

用户可以修改：

- 单元格内容
- 行列结构
- 表头
- Caption

修正后可以重新导出 CSV。

人工修改不能影响原始 PDF。

不要求第一版就实现 Excel 级别的复杂编辑器，
但必须保证基础修改和重新导出可用。

- 作者
- 摘要
- 正文
- Figure Caption
